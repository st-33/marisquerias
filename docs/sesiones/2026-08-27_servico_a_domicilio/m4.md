# Entrega M4 — Dispositivo, operación e interoperabilidad del Repartidor

**Agente:** M4 · **Repositorio:** `st-33/servicio-a-domicilio` · **Rama:** `main`

## Resumen ejecutivo

Se auditó el estado común de los repositorios seleccionados y de las ramas activas antes de modificar código. La rama remota `feat/central-observacion` trabaja la superficie de Central, mientras que M1 publicó en `marisquerias/rama-2` el motor y la integración logística de pedidos. Para no duplicar ni invadir esas zonas, el aporte se ejecutó en el perímetro libre de interoperabilidad del repositorio de Servicio a Domicilio: recepción autenticada de eventos del motor, proyección idempotente de misiones y protección contra replay o eventos fuera de orden.

La entrega conserva el bloque operativo previo del Repartidor: vinculación persistente del dispositivo, acceso por código de un solo uso, validación de tenant y feature flag, ruta directa `/repartidor`, disponibilidad, misión, acciones e incidencias. La mejora nueva añade un receptor HTTP firmado para que M1 pueda publicar una misión compatible sin depender de la sesión web ni de un endpoint público sin identidad de servicio. Durante la auditoría apareció un commit remoto de otro modelo (`bedb69c`, `feat(logistica): agregar proyeccion idempotente de misiones`); se rebasó sobre él, se conservaron sus recibos idempotentes como autoridad para `delivery` y se integró el webhook sin duplicar esa ruta.

> **Principio aplicado:** el dispositivo se configura una vez; el motor es la autoridad de la misión; Central observa señales resumidas; ningún módulo copia pedidos completos ni elude el aislamiento por tenant.

## Arquitectura encontrada y decisiones

La base resolvía usuarios autenticados, membresías, configuración por tenant y feature flags [1] [2]. La autorización de usuario se realiza mediante `getTenantContextForUser` y `requireTenantAccess`; la selección local del tenant no es una frontera de seguridad [3]. El dispositivo opera con una frontera distinta: el servidor valida binding activo, token y tenant antes de devolver misión o aceptar una mutación.

| Frontera | Implementación vigente |
| --- | --- |
| Tenant | Se reutilizan `getTenantContextForTenantId`, `getTenantContextForUser` y `ensureTenantAccess`; un tenant suspendido o sin `courier_assignment` no abre la operación. |
| Dispositivo | `deviceId` estable en el cliente, token aleatorio de vinculación y binding activo único por dispositivo. |
| Código de acceso | `courier.issueCode` está detrás de sesión y propiedad del tenant; el servidor conserva solo `codeHash`, vencimiento y consumo. |
| Sesión operativa | Las aperturas posteriores usan `deviceId` más `bindingToken`; no exigen volver a introducir el código. |
| Motor | `courierMotorWebhook` recibe solo payloads firmados y válidos según el contrato de M1. |
| Proyección | `courier_missions` conserva tipo, estado del motor, tenant, pedido fuente, prioridad y vista mínima para el Repartidor. |
| Observación | Central no recibe pedidos completos desde este bloque; la superficie de observación queda en su rama dedicada. |

## Webhook M1→M4

Se implementó `POST /api/courier/motor/events`. El receptor se monta antes del parser JSON global para verificar el cuerpo crudo con HMAC-SHA256. La configuración requiere `COURIER_MOTOR_WEBHOOK_SECRET`; si no existe, el endpoint responde `503` y no intenta procesar eventos.

El encabezado requerido tiene la forma `x-courier-motor-signature: t=<unix-seconds>,v1=<hex-sha256>`. La firma se calcula sobre `<timestamp>.<raw-body>`, con comparación en tiempo constante y una ventana máxima de cinco minutos. El payload contiene `eventId`, `occurredAt` opcional y `mission`; la misión acepta los dos tipos publicados por M1, `delivery` y `reabastecimiento`, y valida que cada uno incluya su parte receptora (`cliente` o `proveedor`) con ubicación.

| Caso | Respuesta | Comportamiento |
| --- | --- | --- |
| Evento nuevo y válido | `202` | Proyecta o inserta la misión y registra el `eventId`. |
| Mismo evento y mismo payload | `200` | Devuelve `duplicate: true`; no repite la proyección. |
| Mismo `eventId` con otro payload | `409` | Rechaza la colisión para impedir ambigüedad de auditoría. |
| Firma inválida o fuera de ventana | `401` | No parsea ni persiste el evento. |
| Payload inválido | `400` | No persiste datos incompletos o incompatibles. |
| Tenant inexistente, suspendido o sin capacidad | `403` | Aplica la guarda de tenant antes de escribir. |
| Secreto no configurado | `503` | Declara la integración no operativa sin aceptar eventos. |

El registro `courier_motor_events` impone unicidad sobre `eventId` y guarda el hash del cuerpo, tenant, misión, momento de ocurrencia y recepción. La transacción escribe primero la deduplicación y la proyección de misión. Si llega un evento válido pero más antiguo que `sourceUpdatedAt`, registra el evento y devuelve `stale: true` sin retroceder el estado visible.

## Contrato de misión y traducción visual

M1 publica el contrato `RepartoRepository` sobre una RTDB separada, con ruta `reparto/misiones`, misiones `delivery` y `reabastecimiento`, y estados `pendiente`, `asignada`, `en_camino`, `en_ubicacion`, `completada`, `cancelada` y `fallida` [4]. M4 conserva el estado original en `motorStatus` y deriva etiquetas visuales; no introduce estados paralelos como `pickup` o `accepted`.

| Estado del motor | Estado visual | Acciones autorizadas |
| --- | --- | --- |
| `pendiente` | Misión pendiente | Aceptar o rechazar; rechazar mantiene `pendiente`. |
| `asignada` | Asignada | Iniciar recorrido o reportar incidencia. |
| `en_camino` | En camino | Registrar llegada o reportar incidencia. |
| `en_ubicacion` | En ubicación | Confirmar entrega o reportar incidencia. |
| `completada` | Entregada | Ninguna. |
| `cancelada` | Cancelada | Ninguna. |
| `fallida` | Incidencia registrada | Ninguna acción posterior en esta superficie. |

Para `delivery`, la proyección usa `cliente.ubicacion` como destino y metadata opcional para la etiqueta de origen. Para `reabastecimiento`, usa `proveedor.ubicacion` como destino de compra y conserva el tipo de misión para que la UI no lo confunda con una entrega cliente. El identificador de M1 se conserva como `externalId`; `pedidoId`, `tenantPath` y `prioridad` también quedan disponibles en la proyección para el futuro adaptador.

## Bloque operativo del dispositivo

El arranque de `/repartidor` genera o recupera el identificador local del dispositivo. Sin binding muestra acceso inicial; con binding consulta `courier.state`, valida el token, re-resuelve tenant y capacidades y abre directamente la superficie. Un binding revocado, tenant suspendido o flag ausente limpia el contexto local y muestra un error seguro, sin redirigir a Central ni exponer un selector de roles.

La pantalla contiene disponibilidad, misión actual, origen, destino, persona receptora, notas, acciones permitidas e incidencias. Repartidor de planta e independiente comparten aplicación y contrato; `courierType` queda como atributo del actor y no como dos jerarquías de permisos. GPS, mapas, navegación y optimización de rutas permanecen fuera de este bloque.

## Dependencias y bloqueos explícitos

La integración end-to-end con la RTDB de M1 aún requiere que el orquestador elija el transporte definitivo y conecte el `RepartoRepository` con este webhook. El proyector de `delivery` ya está aislado en `server/missionProjection.ts` y el webhook lo reutiliza; la proyección de `reabastecimiento` permanece en la ruta general. La conexión necesita reglas de servicio, secreto gestionado, reintentos con backoff, observabilidad y prueba de conflicto entre estados.

La emisión administrativa de códigos cuenta con endpoint, pero no con pantalla administrativa. Falta decidir rotación, revocación explícita, límite de intentos y auditoría de enrolamiento. También queda abierta la semántica definitiva de `fallida` para incidencias y el almacenamiento de evidencias de entrega. Central debe consumir señales resumidas sin transformarse en propietario de pedidos, asignación o historial.
